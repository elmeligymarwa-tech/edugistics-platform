SECTION H - COURSE DATA
====================================================================

Invent no course names, dates, prices, instructors, venues, durations
or certificates.

THE COURSE COUNT MUST BE DATA-DRIVEN.

The design hardcodes "One course is open for registration right now."
That is true today and false the moment a second course is published.
Delete it. Read the real count from the existing public course data
source. Create no second source of truth and fabricate no count.

Render exactly these three cases:

  count == 1
    "1 course is currently open for registration"

  count >= 2
    "{count} courses are currently open for registration"

  count == 0
    "New training dates are published to the catalogue as they are
     confirmed"

  Note on the zero case: do not write "Explore our upcoming courses" or
  anything implying scheduled dates exist. If the count is zero there
  may be nothing scheduled, and the sentence must stay true either way.

DEFINE "OPEN FOR REGISTRATION" AND REPORT YOUR DEFINITION.

The existing system has courses that are active, archived, full with a
waiting list open, and full with a waiting list closed. A course that is
full with waiting lists closed is not open for registration, because the
submission is rejected.

State plainly in your report:
  which database condition you used
  that archived courses are excluded
  that courses which are full with waiting lists closed are excluded
  whether courses that are full with a waiting list OPEN are counted,
    and your reasoning either way
  the file and function you read the count from

Do not modify the course data source, its queries or its schema. Read
only. If no public read path exists that gives this count without
touching a protected file, stop and report rather than creating one.

If the design contains placeholder course cards, either wire them to
real course data or remove them. Do not ship fabricated cards.

The full catalogue stays on /training.
